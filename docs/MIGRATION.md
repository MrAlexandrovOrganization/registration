# Импорт и первое переключение

## Согласованный сценарий

Источник — актуальная **локальная** SQLite:
`/Users/mrralexandrov/projects/older_05_09_2026/registration-bot/data/database.sqlite`.
Не подменять её старой серверной копией. Переписка остаётся в архиве.
После импорта владелец вручную актуализирует PostgreSQL. Это новый выезд:
все импортированные `state` становятся `new`, ответы сохраняются дословно,
счётчики callback начинаются с нуля. Ранее `registered` не означает готовность.

## 1. Снимок и анализ

Сохранить архивную SQLite с checksum в защищённом хранилище вне VM.
Нужен согласованный standalone snapshot без активного WAL/journal. Для живого
SQLite использовать backup API, а не копировать один файл из работающей БД.
Импортёр открывает `mode=ro&immutable=1`, проверяет quick_check и hash до/после.
Исходный файл нельзя менять параллельно чтению; immutable требует именно offline snapshot.

```sh
make build
.bin/registration import-sqlite --source /absolute/path/database.sqlite --dry-run
```

Вывод содержит только агрегаты, checksum, отсутствующие/невалидные поля.
ФИО, телефоны, сообщения и Telegram ID не выводятся. Невалидное значение не
выбрасывается при импорте: его нужно исправить либо очистить перед открытием.
Старое `Жду ответа по этому году ❗` не является ответом на новый вопрос —
его следует заменить актуальным вариантом или NULL вручную.

## 2. Подготовить PostgreSQL

Остановить frontend и backend; запускать только PostgreSQL и отдельные CLI-команды.
Создать отдельную PostgreSQL и выполнить `make migrate`. Для host CLI экспортировать
`DATABASE_URL`; не выводить его и не подставлять секрет литералом в историю shell.

```sh
.bin/registration import-sqlite --source /absolute/path/database.sqlite
```

Импорт требует пустые предметные/операционные таблицы, блокирует их на время
транзакции и переносит всё атомарно. Сохраняет ID, nullable поля, flags, timestamps,
права без строк users, назначения чатов; identity sequences корректируются.
Legacy timestamps без offset трактуются как UTC (старый код записывал UTC).
`messages` не импортируются. Импорт не создаёт исходящих заданий.

Повтор того же hash — no-op. Другой hash в непустую БД — отказ. Это защищает
ручные изменения; не удалять `import_runs` ради повторного импорта.

## 3. Ручная актуализация

Редактировать можно через SQL-клиент на loopback PostgreSQL, до запуска бота.
Очищать устаревшие ответы через NULL. `state` оставить `new`; не проставлять
`registered` массово. Завершение анкеты потребует явного подтверждения человека.
`NULL`, пустая строка и whitespace означают, что ответ нужно получить снова.

Сохранённые варианты:
- `will_drive`: `Обязательно! 🤩`, `Пока думаю 🤔`, `Не смогу 😢`;
- `trip_attendance`: `Да, точно еду! ✅`, `Нет, не смогу 😢`.

`make validate-data` показывает missing и invalid по полям. Missing допустимы
и будут запрошены ботом; непустые invalid дают ненулевой exit code.
Ручные правки при работающем боте не поддерживаются: они обходят version,
валидацию и аудит. Остановить приём перед SQL-редактированием.

Отдельно проверить административные права: старая SQLite содержит не все
настройки из Python `.env` (`ADMIN_IDS`, `TABLE_GETTERS`, ROOT). Автоматического
чтения старого `.env` нет. Назначить `ROOT_ID`, сверить права и при необходимости
добавить их через команды root или контролируемый SQL до старта.
`staff`-permission и flags роли сохраняются независимо. Событие ухода из чата
меняет flag, но не отнимает вручную выданные административные полномочия.

## 4. Готовность инфраструктуры

1. Проверить миграцию, агрегаты, роли, служебные чаты и резервное восстановление.
2. Заменить тексты `/about`, `/bring` и вопросов в frontend на сведения о новом выезде.
3. Проверить доступность Kafka по Docker-сети, создать только топики регистрации
   командой `init-topics`; не изменять чужие топики.
4. Проверить одинаковые BOT_ID, BACKEND_TOKEN, KAFKA_TOPIC_PREFIX в обоих приложениях.
5. Проверить актуальность схемы; кнопки старого формата отклоняются, пользователи открывают `/start`.
6. Сделать backup подготовленной PostgreSQL до начала новых записей.

## 5. Переключение

Опубликовать независимые репозитории и пройти CI. Развёртывание выполняется
отдельно через согласованный workflow; текущий CI только проверяет и собирает.
Остановить Python polling и убедиться, что он не перезапускается автоматически.
Не запускать два разных получателя updates для одного bot token.
Если ранее был webhook, его снятие — отдельная операция переключения, не startup.

Запустить backend через `make up`, затем
запустить frontend через `make up`. Проверить readiness, анкету контролируемого аккаунта,
малую целевую рассылку, счётчики очереди и поиск тестового trace в Grafana.
Подтверждение CI само по себе не подтверждает успешное переключение.

## Откат

До новых записей: остановить новый frontend, сохранить диагностические агрегаты,
вернуть предыдущую конфигурацию и единственного старого получателя updates.
После новых ответов **нельзя просто включить старую SQLite**: ответы и статусы
доставки останутся только в PostgreSQL. Остановить приём, сохранить PostgreSQL,
исправлять вперёд либо отдельно проектировать обратный перенос.

При откате версии Go оставлять совместимую PostgreSQL, не откатывать данные
вслепую. Восстановление backup возвращает также delivery statuses: оно может
привести к повторной отправке уже доставленных сообщений. После restore сначала
остановить frontend/backend и сверить активные рассылки до их запуска.
